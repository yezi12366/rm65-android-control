# 拖动轨迹保存排查与修复（1.13.1）

用户现象：动作库一直显示“控制器中没有轨迹”。本次未连接实体机械臂，控制器实际代际及固件支持尚未确认。

## 已复现的代码缺陷

1. `RobotResponseParser` 对 `get_trajectory_file_list` 的回复，无论是否存在有效 `list` 字段，都创建轨迹列表；缺字段或明确返回 `receive_state=false` 被变成空列表。前端一律将空数组显示为“没有轨迹”，掩盖接口失败和不兼容。原代码在三个列表回复回归用例中全部失败。
2. 原 `finalizePendingDragSave()` 即使列表中找不到目标名称，也创建 `pointCount=0, verified=true` 的拖动节点，并显示保存成功。这使动作库可能引用根本不存在的控制器文件。
3. 开始录制没有等待成功确认，停止/保存/列表确认没有超时退出；录制中的“结束并保存”按钮被禁用，必须分两次结束，且保存确认失败时容易卡住。

## 修复后的行为

- 连接后自动请求软件信息及轨迹文件列表；区分未查询、查询中、查询失败和已确认的空列表。型号与软件原始字段用于诊断，不猜测代际。
- 以控制器有效列表回复确认文件接口可用，再开放拖动文件录制。
- `DragRecordingFlow` 管理开始、录制、停止、保存、列表验证、失败状态；只接受当前阶段的正确成功字段。
- 支持录制中直接“结束并保存”。仅在控制器文件列表确认同名、非零点数后加入节点并保存动作库。列表尚未刷新时有限重试。
- 缺失回复、命令失败或空轨迹明确报错，不生成成功记录。保存过程中禁止夹爪/等待节点混入；取消、停止和进入后台会终止流程并忽略该流程随后到达的回复。
- 保留已保存的控制器文件，支持取消后刷新并从真实起点导入。
- 执行旧动作前也会核对它引用的控制器文件是否存在且非空，避免旧版误报成功的数据先触发自动回起点，再因缺失文件失败。

## 协议兼容性疑点

现有工程采用官方[第四代轨迹文件接口](https://develop.realman-robotics.com/robot4th/json/trajectoryfile/)。用户最初给出的文档位于第三代控制器目录；[第三代拖动示教接口](https://develop.realman-robotics.com/robot/json/dragTech/)中的 `save_trajectory` 返回拖动点位，与 `save_trajectory_file` 文件管理不是同一条路径。因此仍需通过新版本的实际软件信息和列表回复，确认本机是否支持文件接口。

本次没有把第三代轨迹点读取直接改成普通 `movej` 回放，也没有假定控制器内存中的最近一次拖动轨迹等同已持久保存的文件。若设备确实不支持文件接口，需按其固件支持另行实现轨迹读取、存储和对应的回放路径。

## 验证

- 24 个 Kotlin/JUnit 用例通过，含开始/停止/保存拒绝、各阶段超时、文件延迟出现、同名匹配、空轨迹、旧版错误动作、重复请求、取消和错误字段解析。
- 网页 JavaScript 语法检查、3 个现有动作域测试通过；界面事件检查覆盖查询中/失败/真实空列表、软件信息及开始/录制/保存/失败时的按钮行为。
- 全部生产 Kotlin 源码使用 Google 官方 Android API 35 的 `android.jar` 通过编译检查；此检查采用临时资源 ID 声明，未进行 Gradle 资源打包或生成 APK。未完成实机保存及回放验收。完整 Android 构建请在配置好 JDK 17 与 Android SDK 35 后运行 `./gradlew testDebugUnitTest assembleDebug`。
